# Валидация

## Как проверяются входные данные

За проверку данных отвечает Symfony Validator, а правила описываются PHP-атрибутами.
`config/definitions/validator.php` создает `ValidatorInterface` через `Validation::createValidatorBuilder()->enableAttributeMapping()->getValidator()`.
Вызывать проверку удобно через `App\Validation\InputValidator` и его метод `validate(object $input): void`.

В контроллере данные из запроса передаются в объект `Input`, после чего вызывается `InputValidator::validate()`.
Если значения корректны, выполнение продолжается и данные передаются в сервис.
Если нет, клиент получает ответ с описанием ошибок.

## Проверка типов и значений

Данные из HTTP-запроса нельзя считать корректными заранее. 
Вместо строки клиент может отправить число, массив или `null`. 
Если сразу объявить входное свойство как `string`, неподходящее значение может вызвать `TypeError` ещё до проверки ограничений.

Поэтому в существующих входных DTO используются свойства типа `mixed`. 
Их фактический тип проверяется через `Assert\Type`, а остальные ограничения определяют допустимое значение.

```php
use Symfony\Component\Validator\Constraints as Assert;

final class TitleInput
{
    public function __construct(
        #[Assert\Sequentially([
            new Assert\Type('string', message: 'Ожидается строка'),
            new Assert\NotBlank(normalizer: 'trim', message: 'Заполните поле'),
            new Assert\Length(max: 120, maxMessage: 'Не больше {{ limit }} символов'),
        ])]
        public mixed $title,
    ) {}
}
```

Здесь `Sequentially` выполняет ограничения по порядку и останавливается после первой ошибки. 
Например, если вместо названия пришёл массив, проверка длины строки уже не выполняется.

В контроллере создание и проверка объекта выглядят так:

```php
$body = $request->getParsedBody();
$input = new TitleInput($body->title ?? null);
$validator->validate($input);
```

Здесь `$validator` - внедренный `InputValidator`, а `$request` - текущий HTTP-запрос.

После успешной валидации значения соответствуют заданным ограничениям.

## Как возвращаются ошибки

Если какое-либо ограничение нарушено, `InputValidator` собирает сообщения по именам свойств и выбрасывает `ValidationException`. 
Централизованный обработчик ошибок преобразует его в JSON-ответ со статусом **422 Unprocessable Content**:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте введенные данные",
    "details": {"title": ["Заполните поле"]}
  }
}
```

Некорректный JSON и неподходящая структура тела запроса отклоняются раньше, на уровне HTTP middleware, со статусом **400 Bad Request**. 
Для POST, PUT и PATCH в стартере по умолчанию требуется JSON-объект, даже если полей нет. 
В таком случае можно отправить `{}` с заголовком `Content-Type: application/json`. 
Для multipart-загрузки аватара предусмотрено отдельное исключение.

Валидация отвечает за форму и допустимые значения входных данных, но не заменяет бизнес-проверки и авторизацию. 
Например, email может соответствовать всем ограничениям, но уже быть занят другим пользователем. 
Такие ситуации обрабатываются отдельно.

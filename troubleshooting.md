# Диагностика проблем

## Проверка работы приложения

Для начала посмотрите состояние контейнеров, доступность API и последние записи журналов:

```bash
./run ps
curl -i http://localhost:8080/health/live
curl -i http://localhost:8080/health
./run logs --tail=100 app worker
```

Эндпоинт `/health/live` проверяет, что HTTP-приложение отвечает, не обращаясь к Doctrine и Redis. 
`/health` дополнительно проверяет готовность зависимостей. 
Поэтому успешный ответ `/health/live` еще не означает, что приложение может работать с базой данных.

Если интерфейс открывается, но запросы к `/api/...` не проходят, проверьте адрес API и настройку прокси Vite. 
При локальном запуске запросы направляются на `http://127.0.0.1:8080`, а внутри frontend-контейнера - на `http://nginx`.

## Ошибки базы данных и миграций

Исключение `TableNotFoundException` обычно появляется, когда необходимые миграции еще не применены или приложение подключается не к той базе данных. 
Ошибка может возникнуть как в API, так и в разделах очереди и вебхуков терминальной панели.

Проверьте состояние миграций и при необходимости примените их:

```bash
./run doctrine migrations:status --no-interaction
./run migrate --no-interaction
```

Если ошибка остается, сравните `DB_HOST`, `DB_PORT` и `DB_NAME` у приложения и процесса, выполняющего миграции.

Для очереди используется таблица `messenger_messages`, а для вебхуков - `webhook_deliveries` и `webhook_attempts`. 
Эти таблицы создаются миграциями, поэтому не стоит создавать их вручную или удалять Docker volume ради исправления ошибки. 
Удаление тома приведет к потере сохраненных данных.

Подробнее о работе со схемой данных можно прочитать в разделе [База данных](/docs/{{version}}/database).

## Не выполняются фоновые задачи и отправка писем

Добавление задания в очередь не означает, что оно уже выполнено. Для обработки сообщений нужен отдельный worker.

Запустите его и проверьте состояние очереди:

```bash
./run --profile queue up -d worker
./run console queue:stats
./run console queue:failed
./run logs --tail=100 worker
```

В локальном Docker-окружении отправленные письма можно посмотреть в Mailpit по адресу http://localhost:8025.

Если письмо появилось в Mailpit, но ссылка в нем ведет не туда, проверьте `FRONTEND_URL`. 
Если письма нет, проверьте, было ли создано задание, зарегистрирован ли его обработчик и доступен ли SMTP-сервер.

После изменения `.env` пересоздайте соответствующие контейнеры. 
Уже запущенные процессы не получают обновленные значения окружения автоматически.

Подробнее: [Очереди](/docs/{{version}}/queues) и [Почта](/docs/{{version}}/mail).

## HTTP-ошибки

HTTP-статус помогает определить, в каком направлении искать причину:

| Статус                      | Что проверить                                                                                                                     |
|-----------------------------|-----------------------------------------------------------------------------------------------------------------------------------|
| `400 Bad Request`           | Формат JSON, `Content-Type` и структуру тела запроса. Для POST, PUT и PATCH нужен JSON-объект, в том числе `{}` для пустого тела. |
| `401 Unauthorized`          | Access-токен, refresh-cookie и состояние серверной сессии.                                                                        |
| `403 Forbidden`             | Подтверждение email и разрешение на конкретное действие.                                                                          |
| `404 Not Found`             | Адрес маршрута и существование запрошенного ресурса.                                                                              |
| `422 Unprocessable Content` | Поле `error.details` с результатами валидации.                                                                                    |
| `429 Too Many Requests`     | Ограничение частоты запросов и интервал из заголовка `Retry-After`.                                                               |
| `500 Internal Server Error` | Исходное исключение в серверных логах.                                                                                            |

Для ошибки `500` полезно найти запрос по `X-Request-ID`: этот идентификатор связывает ответ API с записью в журнале. 

## Изменение настроек окружения

При использовании Docker переменные из `.env` передаются контейнерам во время их создания. Чтобы приложение и worker получили обновленные значения, их необходимо пересоздать:

```bash
./run --profile queue up -d --force-recreate app worker
```

# Вебхуки

Вебхуки позволяют приложению сообщать внешним сервисам о произошедших событиях с помощью HTTP-запросов.

За отправку отвечает `App\Webhooks\Webhooks`. 
Сервис сохраняет доставку в PostgreSQL и отправляет задание `DeliverWebhook` в очередь. 
Состояние доставки и результаты попыток записываются в таблицы `webhook_deliveries` и `webhook_attempts`.

## Настройка получателей

Получатели и события настраиваются в `config/settings/webhooks.php`. В стартере предусмотрены отдельные параметры для событий пользователей и уведомлений:

| Получатель            | Адрес                      | Секрет                        |
|-----------------------|----------------------------|-------------------------------|
| События пользователей | `WEBHOOK_USER_URL`         | `WEBHOOK_USER_SECRET`         |
| Уведомления           | `WEBHOOK_NOTIFICATION_URL` | `WEBHOOK_NOTIFICATION_SECRET` |

Для каждого получателя также задан список событий, на которые он подписан. 
Например, пользовательский endpoint может принимать `user.registered`, `user.verified`, `user.updated`, `user.password_reset` и `user.demo`.

Отправить событие можно через `Webhooks`, полученный с помощью DI:

```php
use App\Webhooks\Webhooks;

final class DemoWebhookService
{
    public function __construct(private Webhooks $webhooks) {}

    public function send(): array
    {
        return $this->webhooks->dispatch('user.demo', ['userId' => 42]);
    }
}
```

`dispatch()` возвращает массив идентификаторов созданных доставок. 
Если для события нет подходящих получателей, массив будет пустым. 
Для подключения нового события нужно добавить его имя в список `events` нужного получателя.

Каждая доставка выполняется через [очередь](/docs/{{version}}/queues), поэтому для отправки требуется работающий worker. 

## Формат запроса и подпись

Тело вебхука содержит идентификатор события `id`, его имя `event`, время возникновения `occurredAt` в UTC и полезную нагрузку `data`. 
Для каждого получателя создаётся отдельная доставка со своим идентификатором.

В HTTP-запрос добавляются заголовки:

- `X-Webhook-Id` - идентификатор доставки.
- `X-Webhook-Event` - название события.
- `X-Webhook-Timestamp` - время отправки.
- `X-Webhook-Signature` - подпись запроса.

Идентификатор события в JSON и идентификатор доставки в заголовке отличаются. Это важно учитывать при регистрации и обработке повторных запросов.

Подпись формируется с помощью HMAC-SHA256 и имеет префикс `v1=`:

```php
$signature = 'v1=' . hash_hmac(
    'sha256',
    $deliveryId . '.' . $timestamp . '.' . $rawBody,
    $secret,
);
```

Получатель должен вычислить подпись по **исходному телу HTTP-запроса**. Если сначала декодировать JSON, а затем сформировать его заново, подпись может не совпасть.

Для проверки предусмотрен `App\Webhooks\WebhookSignature::verify()`. 
Метод использует `hash_equals()` и по умолчанию допускает расхождение времени до 300 секунд. 
Поэтому часы отправителя и получателя должны быть синхронизированы.

На стороне получателя также стоит сохранять уже обработанные `X-Webhook-Id`, чтобы повторная доставка не приводила к повторному выполнению одного действия.

## Локальная проверка

В `tools/webhook-receiver.php` есть простой получатель для тестирования вебхуков. 
Он принимает POST-запросы, проверяет подпись с помощью `WEBHOOK_USER_SECRET` и ограничивает размер тела одним мегабайтом.

Переменная `WEBHOOK_RECEIVER_STATUS` позволяет имитировать ответ с ошибкой и проверить механизм повторных попыток.

Если получатель запущен на хосте, учитывайте сетевое окружение Docker. 
Адрес `localhost` внутри worker указывает на сам контейнер, а не на компьютер, на котором запущен Docker.

## История доставок и повторные попытки

Для просмотра состояния вебхуков предусмотрены консольные команды:

```bash
./run console webhooks:deliveries
./run console webhooks:deliveries DELIVERY_ID
./run console webhooks:retry DELIVERY_ID
```

Первая команда показывает последние доставки, вторая - историю попыток выбранной доставки. 
Третья запускает повторную отправку с тем же идентификатором, если доставка ещё не была успешно завершена.

Повтор вебхука отличается от `queue:retry`: команда `webhooks:retry` работает с идентификатором доставки, а `queue:retry` - с идентификатором сообщения в транспорте неудачных заданий.

Успешным считается любой ответ со статусом **2xx**. 
Автоматические повторы выполняются при сетевых ошибках, статусах 5xx, а также 408, 425 и 429. 
Другие HTTP-ошибки и проблемы конфигурации считаются невосстановимыми для текущего задания.

При отправке отключены перенаправления. 
Таймаут ожидания составляет пять секунд, а максимальная длительность запроса - десять секунд.

Если вебхук не доставляется, сначала проверьте историю попыток, затем URL и секрет получателя, а также логи worker. 
После изменения переменных окружения пересоздайте соответствующие процессы и при необходимости повторите доставку.

**Важная особенность:** вебхук может быть доставлен повторно, даже если внешний сервис уже выполнил действие. 
Поэтому обработчик на стороне получателя должен учитывать дубли, например по идентификатору доставки.

Подробнее о фоновой обработке и событиях приложения можно прочитать в разделах [Очереди](/docs/{{version}}/queues) и [События](/docs/{{version}}/events).

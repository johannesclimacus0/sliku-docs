# Контроллеры

## Роль контроллера

Контроллер принимает запрос и возвращает ответ.
Контроллеры находятся в `src/Modules/*/Controllers/` и представляют собой обычные PHP-классы.
Нужные зависимости указываются в конструкторе, а создает их PHP-DI.

Метод получает `ServerRequestInterface` и `ResponseInterface`.
Это объекты PSR-7: в запросе лежат заголовки, параметры и разобранное тело, в ответе - статус, заголовки и поток тела.
Методы вроде `withHeader()` возвращают новый ответ, поэтому результат нужно присвоить или вернуть.

## Простой контроллер

Для формирования JSON-ответов в стартере предусмотрен `App\Http\JsonResponse`. 
Его можно получить через конструктор, как и другие зависимости:

```php
namespace App\Modules\Account\Controllers;

use App\Http\JsonResponse;
use Psr\Http\Message\ResponseInterface;

final class StatusController
{
    public function __construct(private JsonResponse $json) {}

    public function __invoke(ResponseInterface $response): ResponseInterface
    {
        return $this->json->success($response, ['status' => 'ok']);
    }
}
```

Такой контроллер можно подключить в `routes/api.php`:

```php
$app->get('/status', StatusController::class);
```

Метод `__invoke()` используется, когда у контроллера одно действие. 
Для контроллера с несколькими методами маршрут указывает конкретный метод, например `SomeController::class . ':show'`.

## Входные данные и валидация

В реальных запросах обычно требуется больше, чем просто вернуть ответ. 
Например, `AuthController::register()` получает данные через `$request->getParsedBody()`, создаёт `RegisterInput`, проверяет его с помощью `InputValidator::validate()` и передаёт проверенные значения в `AuthService`.

В таком сценарии у каждого компонента своя задача: контроллер работает с HTTP, объект `Input` описывает входные данные, валидатор проверяет их, а сервис выполняет регистрацию. 
После этого контроллер возвращает результат клиенту.

## Текущий пользователь и проверка прав

В `UserController::show(User $user, ...)` объект `User` загружается из параметра маршрута через механизм привязки сущностей. 
При этом текущий авторизованный пользователь определяется отдельно с помощью `AuthenticatedUser::fromRequest($request)`.

Это не обязательно один и тот же пользователь. Поэтому успешная загрузка сущности ещё не означает, что к ней разрешён доступ.

Например, перед выдачей профиля контроллер проверяет право просмотра через `denyAccessUnlessGranted()` и `UserVoter::VIEW`. 
В сценарии изменения профиля проверка прав выполняется в `ProfileService`, а контроллер отвечает за входные данные и вызов сервиса.

## Обработка ошибок

Ошибки приложения обрабатываются централизованно через `JsonErrorHandler`. 
Он преобразует исключения в JSON-ответы.

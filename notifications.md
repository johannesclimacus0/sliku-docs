# Уведомления

Уведомления позволяют сообщать пользователям о событиях в приложении. 
Они могут сохраняться в личном кабинете, отправляться по электронной почте или доставляться через несколько каналов одновременно.

За создание уведомлений отвечает `App\Notifications\Notifications`. 
Метод `send(int $userId, Notification $notification): string` отправляет задание `SendNotification` в очередь и возвращает идентификатор уведомления. 
Само уведомление обрабатывается позже, поэтому полученный идентификатор ещё не означает, что запись появилась в базе данных или письмо было отправлено.

## Создание уведомления

Класс `App\Notifications\Notification` расширяет Symfony Notification. 
В нём задаются тема, текст, каналы доставки, тип уведомления и дополнительные данные.

Например, сообщение о готовности отчёта можно отправить в личный кабинет и на почту:

```php
use App\Notifications\Notification;
use App\Notifications\Notifications;

final class ReportNotifier
{
    public function __construct(
        private Notifications $notifications,
    ) {}

    public function ready(int $userId): string
    {
        return $this->notifications->send($userId, new Notification(
            subject: 'Отчет готов',
            content: 'Откройте раздел отчетов.',
            channels: ['database', 'email'],
            type: 'report.ready',
            data: ['url' => '/reports'],
        ));
    }
}
```

Сервис `Notifications` можно получить через DI, указав его в конструкторе. 
По умолчанию уведомления отправляются только в канал `database`, имеют тип `general` и не содержат дополнительных данных.

Для каждого уведомления создаётся идентификатор из 32 строчных hex символов. 
Дополнительные данные должны подходить для сериализации в сообщение очереди и хранения в JSON.

## Каналы доставки

В стартере настроены два канала, `database` и `email`. 
Их определения находятся в `config/definitions/notifier.php`.

После получения задания `SendNotificationHandler` находит пользователя через `UserRepository`, создаёт `UserRecipient` и передаёт уведомление в Symfony Notifier. 
Если пользователь уже удалён, обработка завершается без доставки.

- `database` сохраняет уведомление через `NotificationStore`, чтобы его можно было показать в личном кабинете.
- `email` отправляет письмо с помощью `MailClient` и шаблона `templates/emails/notification.html.twig`. Для этого должна быть настроена [почта](/docs/{{version}}/mail).

Для добавления собственного канала понадобится его реализация и регистрация в Symfony Notifier. 
Просто указать новое имя в `channels` недостаточно.

Задание `SendNotification` уже связано с обработчиком в `config/registrations/jobs.php`. 
При создании собственных подклассов `Notification` менять эту регистрацию не нужно. 
Например, `src/Modules/Account/Notifications/AccountNotification.php` формирует уведомления на основе событий аккаунта.

## Чтение уведомлений

Сохранённые уведомления доступны через `App\Notifications\NotificationStore`. 
Сервис позволяет получать список, считать непрочитанные сообщения и отмечать их как прочитанные.

```php
use App\Notifications\NotificationStore;

function inbox(NotificationStore $store, int $userId): array
{
    return $store->list($userId, page: 1, unreadOnly: true);
}
```

Метод `list()` возвращает `items`, `unreadCount` и `pagination`. 
На одной странице размещается 20 уведомлений.

Для работы с состоянием доступны следующие методы:

| Метод                                     | Назначение                                  |
|-------------------------------------------|---------------------------------------------|
| `unreadCount(int $userId): int`           | Количество непрочитанных уведомлений        |
| `markRead(int $userId, string $id): bool` | Отметка одного уведомления как прочитанного |
| `markAllRead(int $userId): void`          | Отметка всех уведомлений пользователя       |

В `list()` следует передавать положительный номер страницы, а в методы хранилища - идентификатор нужного пользователя. 
`NotificationStore` сам по себе не проверяет права на HTTP-запрос, поэтому доступ к чужим уведомлениям необходимо ограничивать на уровне приложения.

## Фоновая обработка и повторная доставка

Для сохранения уведомлений нужна соответствующая таблица в базе данных, а для выполнения заданий - работающий [worker](/docs/{{version}}/queues). 
Автоматические уведомления о событиях аккаунта создаёт `UserLifecycleSubscriber`. 
С уведомлениями также связаны [вещание](/docs/{{version}}/broadcasting) и [вебхуки](/docs/{{version}}/webhooks), но необходимые для них внешние сервисы запускаются отдельно.

Повторная обработка задания не всегда должна приводить к повторной доставке. 
При сохранении в БД используется защита от дубликатов по паре `(id, user_id)`, а событие `NotificationCreated` отправляется только при создании новой записи. 
Аналогично `NotificationRead` отправляется лишь тогда, когда состояние уведомления действительно изменилось.

С отправкой писем ситуация другая: при повторном выполнении задания письмо может уйти ещё раз.
Если это недопустимо для конкретного сценария, потребуется дополнительная защита от повторной отправки.

Если `send()` вернул идентификатор, но уведомление не появилось в личном кабинете, проверьте состояние очереди, наличие пользователя и выбранные каналы.

# Контейнер зависимостей

## Для чего нужен контейнер

Компоненты приложения редко работают сами по себе. 
Например, контроллер регистрации использует сервис аутентификации, валидатор и инструмент для формирования JSON-ответов.
Этим компонентам, в свою очередь, могут потребоваться другие зависимости.

Чтобы не создавать и не настраивать всю цепочку объектов вручную, стартер использует PHP-DI. 
Контейнер создаёт необходимые экземпляры и передаёт их в конструкторы классов. 
Благодаря этому зависимости остаются явными, а при тестировании их проще заменить.

Сборка контейнера начинается в `config/container.php`:

1. Загружаются файлы из `config/registrations/*.php`. Их содержимое становится доступно по ключам `registrations.<имя файла>`.
2. Затем в отсортированном порядке загружаются определения из `config/definitions/*.php` и добавляются в `ContainerBuilder`.
3. В результате создаётся контейнер, реализующий `DI\Container`.

Если несколько файлов определяют один ключ, более позднее определение может заменить предыдущее. 

## Автоматическое создание классов

Для многих классов не требуется отдельная регистрация. 
PHP-DI может самостоятельно создать объект, если зависимости в его конструкторе имеют подходящие типы и доступны контейнеру.

Например, сервис может получать настройки приложения через `Config`:

```php
namespace App\Modules\Account\Services;

use App\Config\Config;

final class AccountTitle
{
    public function __construct(private Config $config) {}

    public function get(): string
    {
        return $this->config->get('app.app_name', 'Sliku');
    }
}
```

При создании `AccountTitle` контейнер предоставит экземпляр `Config`.
Самому сервису не нужно знать, где и как загружаются настройки.

## Определения и фабрики

По одному интерфейсу контейнер не может угадать, какой именно класс нужен.
С параметром `string` похожая ситуация: тип есть, а само значение откуда-то нужно взять.
Такие зависимости настраиваются в `config/definitions/`.

Пример определения значения:

```php
use App\Config\Config;

return [
    'application.title' => static fn (Config $config): string =>
        $config->get('app.app_name', 'Sliku'),
];
```

Значение можно получить через `$container->get('application.title')` в коде сборки.

Реальный пример связывания интерфейса находится в `config/definitions/doctrine.php`: `EntityManagerInterface` ссылается на `EntityManager` через `DI\get()`.
Сам менеджер создается фабрикой с `Config`, `Profiler` и кэшем.

## Регистрации компонентов

Помимо определений зависимостей, в проекте есть каталог `config/registrations/`. 
Он содержит списки компонентов, которые подключаются к отдельным механизмам приложения: команды, обработчики событий, правила доступа и другие расширения.

Например, `config/definitions/security.php` использует список `registrations.voters` для настройки `AccessDecisionManager`.

Важно различать **создание класса** и **его подключение к определённому механизму**. 
Контейнер может создать объект, но это ещё не делает его консольной командой, слушателем события или HTTP-обработчиком. 
Соответствующий компонент должен быть зарегистрирован там, где его ожидает приложение.

## Контейнер и HTTP-запросы

При запуске приложения PHP-DI Bridge связывает контейнер со Slim. 
После определения подходящего маршрута `RouteEntityBindingStrategy` подготавливает параметры обработчика и вызывает его через `$container->call()`.

Это позволяет использовать внедрение зависимостей и при вызове контроллеров.

Подробнее о связанных механизмах можно прочитать в разделах [Конфигурация](/docs/{{version}}/configuration), [Контроллеры](/docs/{{version}}/controllers) и [Авторизация](/docs/{{version}}/authorization).

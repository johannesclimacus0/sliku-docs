# Аутентификация

За вход и сессии отвечает модуль `App\Modules\Auth`.
После входа клиент получает JWT с небольшим сроком жизни, а в PostgreSQL остается refresh-сессия.
При каждом защищенном запросе сервер проверяет не только access-токен, но и то, что связанная с ним сессия еще активна.

## Регистрация и вход

Регистрация выполняется через `POST /auth/register`, а вход - через `POST /auth/login`. При входе можно передать булевое поле `remember`, чтобы увеличить длительность сессии.

Успешный ответ содержит `access_token`, `token_type: Bearer` и `expires_in: 900`. Последнее значение означает, что access-токен действует 15 минут.

Пример входа с демонстрационной учётной записью:

```bash
curl -i -c cookies.txt \
  -H 'Content-Type: application/json' \
  -d '{"email":"member@example.test","password":"ChangeMe12345!","remember":true}' \
  http://localhost:8080/auth/login
```

Для обновления access-токена используется `POST /auth/refresh`. Refresh-токен передаётся в cookie, а не в теле запроса:

```bash
curl -i -b cookies.txt -c cookies.txt \
  -H 'Content-Type: application/json' \
  -d '{}' \
  http://localhost:8080/auth/refresh
```

В примерах используются адреса backend напрямую. При обращении через Vite к путям добавляется префикс `/api`, который прокси удаляет перед передачей запроса.

## Защищённые запросы

Access-токен передаётся в заголовке `Authorization: Bearer <token>`. `JwtAuthMiddleware` проверяет токен и сессию, находит пользователя и добавляет его в атрибуты запроса. 
В контроллере получить текущего пользователя можно через `AuthenticatedUser::fromRequest($request)`.

Для проверки текущей авторизации предусмотрен маршрут `GET /auth/me`.

JWT подписывается алгоритмом HS256 с помощью `JWT_KEY` длиной не менее 32 байт. 
Токен содержит claims `sub`, `sid`, `iat` и `exp`. 
Значение `sid` связывает JWT с записью в таблице `refresh_sessions`.

## Срок действия и обновление сессии

Access-токен действует 15 минут. Refresh-токен представляет собой случайную строку, от которой в базе хранится только SHA-256-хэш.

При каждом обновлении refresh-токен ротируется: старая запись атомарно удаляется, а новый токен выдаётся с прежним `session_id`.

Обычная refresh-сессия действует 12 часов после выдачи или последней ротации. 
При `remember: true` срок составляет 365 дней от последней ротации.
В обоих случаях успешное обновление продлевает сессию. 

Refresh-токен хранится в cookie. 
Без `remember` создаётся cookie на время браузерной сессии.

В окружениях, отличных от `APP_ENV=local`, cookie получает флаг `Secure`.

## Выход и отзыв сессий

Маршрут `POST /auth/logout` удаляет текущую refresh-сессию и очищает cookie. 

При успешном сбросе пароля приложение отзывает все сессии пользователя. 

## Подтверждение почты и восстановление пароля

Подтверждение адреса электронной почты выполняется через `POST /auth/email/verify`. 
Для повторной отправки письма предусмотрен защищённый маршрут `POST /auth/email/verification-notification`.

Восстановление пароля начинается с `POST /auth/forgot-password` и завершается через `POST /auth/reset-password`.

Письма отправляются через [очереди](/docs/{{version}}/queues), поэтому для их доставки нужен запущенный worker.

Настройки этих механизмов задаются переменными окружения:

| Переменная                    | Назначение                                            |
|-------------------------------|-------------------------------------------------------|
| `EMAIL_VERIFICATION_REQUIRED` | Требовать подтверждение почты для защищённых действий |
| `EMAIL_VERIFICATION_TTL`      | Срок действия подтверждения, по умолчанию 3600 секунд |
| `PASSWORD_RESET_TTL`          | Срок действия сброса пароля, по умолчанию 1800 секунд |
| `FRONTEND_URL`                | Адрес интерфейса, используемый в ссылках из писем     |

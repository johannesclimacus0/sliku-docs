# Очереди

Очереди позволяют выполнять задачи в отдельном процессе, не заставляя HTTP-запрос ждать их завершения.

Для этого используется Symfony Messenger с транспортом Doctrine.
Отправка сообщений вынесена в сервис `App\Queue\Queue`, который можно получить через DI и вызвать его метод `dispatch(object $job): void`.

После успешного вызова `dispatch()` сообщение передано транспорту, но сама задача ещё не обязательно выполнена. 
За её обработку отвечает отдельный процесс - worker.

## Настройка очереди

Параметры находятся в `config/settings/queue.php`. 
В стартере настроены таблица `messenger_messages`, основная очередь `async`, транспорт для ошибок `failed` и повторные попытки выполнения.

Транспорт использует соединение Doctrine с PostgreSQL. Поэтому перед работой с очередью необходимо [настроить базу данных](/docs/{{version}}/database) и применить миграции. 
Параметр `auto_setup` отключён: Messenger не создаст таблицу при первом обращении.

В `config/definitions/queue.php` правило `'*'` направляет все сообщения в `async`. 
Обёртка `Queue` не предусматривает отдельного синхронного режима.

В сообщения лучше передавать простые сериализуемые данные, например идентификаторы записей. 
Если обработчику понадобится актуальное состояние пользователя, он сможет загрузить его из базы непосредственно перед выполнением задачи.

## Создание задания

В стартере уже есть пример сообщения `App\Queue\Jobs\WriteLog` и его обработчика `App\Queue\Handlers\WriteLogHandler`.

Задание можно отправить из сервиса, получив `Queue` через конструктор:

```php
use App\Queue\Jobs\WriteLog;
use App\Queue\Queue;

final class ReportService
{
    public function __construct(
        private Queue $queue,
    ) {}

    public function start(): void
    {
        $this->queue->dispatch(
            new WriteLog('Начало формирования отчета'),
        );
    }
}
```

Обработчик представляет собой обычный PHP-класс с методом `__invoke(WriteLog $job): void`. 
Когда worker получает сообщение, Messenger вызывает соответствующий обработчик, а его зависимости предоставляет DI-контейнер.

Чтобы связать новое сообщение с обработчиком, добавьте их в `config/registrations/jobs.php`:

```php
return [
    \App\Queue\Jobs\WriteLog::class => \App\Queue\Handlers\WriteLogHandler::class,
];
```

## Запуск worker

В Docker worker запускается отдельно через профиль `queue`:

```bash
./run --profile queue up -d worker
```

Проверить отправку и выполнение задания помогут команды:

```bash
./run console queue:dispatch-log 'Проверка очереди'
./run console queue:stats
./run logs --tail=50 worker
```

Без Docker worker можно запустить вручную:

```bash
php bin/console queue:work async
```

В `compose.yaml` для него предусмотрены ограничения по времени и памяти, параметр `--keepalive=30` и автоматический перезапуск контейнера. 
Само наличие worker в конфигурации Compose не означает, что процесс уже запущен.

После изменения кода обработчиков или настроек окружения worker следует перезапустить, а при изменении переменных, передаваемых через `env_file`, пересоздать контейнер.

## Повторные попытки и ошибки

Если обработчик выбрасывает исключение, Messenger может повторить выполнение задания. 
По умолчанию предусмотрено до трёх повторов с начальной задержкой 1000 мс, множителем 2 и максимальной задержкой 60000 мс.

Если все попытки исчерпаны, сообщение перемещается в `failed`. 
Для просмотра и повторной отправки используются команды:

```bash
./run console queue:failed
./run console queue:retry 1
```

В `queue:retry` передаётся идентификатор сообщения из списка ошибок. К
оманда возвращает его в `async`, после чего счётчик попыток начинается заново. 
Для удаления неудачных сообщений есть `queue:forget`; перед использованием стоит проверить её параметры.

**Повторное выполнение не гарантирует, что предыдущее действие не успело выполниться частично.** 
Например, письмо могло быть отправлено до возникновения ошибки. 
Поэтому обработчики, работающие с внешними системами и важными данными, следует проектировать с учётом возможных повторов.
